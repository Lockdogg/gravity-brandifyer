# Brand Manager Plugin — План разработки

Документ описывает, что мы строим, почему, как это устроено архитектурно, и в какой последовательности это делать. Предназначен для разработчика проекта и для AI-агента (Claude Code), которому передаётся выполнение.

---

## 1. Краткий обзор

Плагин для Figma, позволяющий продуктовому дизайнеру самостоятельно добавить свой "бренд" в центральную дизайн-либу YC Gravity UI, не дёргая DS-команду. На входе — бренд-цвет (и опционально другие параметры), на выходе — новая колонка в коллекции Brand, новая группа в коллекции Appearance с полной обвязкой токенов на 4 темы (Light / Dark / Light HC / Dark HC), сгенерированные private brand-примитивы и CSS-экспорт для фронтенда.

## 2. Контекст и обоснование

**Архитектура внутренней либы (3 уровня):**

- **Private Colors** — примитивы вида `<Brand>/Light/Blue/550 Solid` (RGB значения).
- **Appearance** — брендированные семантические токены `<Brand>/Text/Primary`, `<Brand>/Branding/Base Brand` и т.д. Коллекция имеет 4 модуса: Light / Dark / Light HC / Dark HC. У каждого бренда — около 142 токенов.
- **Brand** — абстрактный слой `--g-color-text-primary`, `--g-color-base-brand` и т.д. Коллекция имеет модусы по числу брендов (сегодня 6: YC, YC 2026, Gravity, Yandex Beta, Orbita, DataLens). Каждый Brand-токен в каждом бренд-модусе алиаситься на соответствующий `<Brand>/...` из Appearance. Сюда же входят типографика и радиусы (общие для всех брендов, не пробрендированы).

Компоненты либы привязаны к Brand-токенам, поэтому смена бренда в рабочем файле = смена модуса коллекции Brand, без ремаппинга алиасов.

**Почему сейчас:**

Раньше Figma давала максимум 4 модуса на коллекцию, что ограничивало число поддерживаемых брендов. Лимит вырос до ~40, и теперь продуктовые команды могут иметь свои "бренды" в общей либе без выселения в отдельные файлы.

**Почему Themer:**

Gravity UI имеет публичный пакет `@gravity-ui/uikit-themer`, реализующий blend-алгоритм генерации private colors из одного бренд-цвета. Не нужно изобретать алгоритм — нужно правильно интегрировать его с Figma Variables API.

**Текущий статус брендов:**

Из 6 существующих брендов реально структурно отличается только Orbita. Остальные — "перекрашенные" наборы поверх общих Private Colors. То есть в подавляющем большинстве случаев новый бренд = переопределение акцентного цвета и Branding-группы, всё остальное наследуется от базового бренда.

## 3. Цели и не-цели

### v1 (in scope)

- Базовый режим: создание бренда из одного бренд-цвета.
- Экспертный режим: то же + подключение собственной либы Private Colors (бывшая логика external-mode плагина Remapper).
- Выбор базового бренда для наследования (дефолт — YC).
- Генерация всех 4 тем (Light / Dark / Light HC / Dark HC) единым blend-алгоритмом с разными primary/contrasting фонами.
- Превью внутри окна плагина без артефактов в файле либы.
- CSS-экспорт в формате Themer'а как загружаемый файл из UI плагина.
- Запуск в ветке центрального файла либы. Ревью — через нативный механизм Figma branches.

### v1 (out of scope)

- Редактирование уже созданных брендов.
- Удаление брендов.
- Миграции рабочих файлов между брендами (это нативный mode-switch коллекции Brand).
- Кастомизация типографики, радиусов, не-Branding токенов (всё это наследуется от базового бренда).
- Code-side пайплайн публикации (плагин даёт CSS-артефакт, как он попадает в репозиторий фронтенда — отдельная история).
- Самовольное создание новых модусов или коллекций — только запись в существующие.

## 4. Архитектура решения

### 4.1. Что плагин записывает в либу

#### Phase 1 — файл приватных цветов нового бренда

> **Изменение архитектуры:** сначала планировали записывать только шкалу акцентного цвета (~31 переменная) прямо в коллекцию Private Colors основной либы. Затем решили выносить приватные цвета каждого нового бренда в **отдельный файл-либу** — потому что файл с приватными цветами должен быть самодостаточным и полным, как у существующих брендов (Yandex Cloud, Gravity и т.д.), которые тоже имеют свои отдельные файлы. Локальная запись в главный файл нарушала бы эту конвенцию.

Плагин запускается в **пустом файле** `<Brand Name> Private Colors` и создаёт коллекцию `Private Colors` с полным набором цветов:

- **`Brand`** (~30 vars на тему) — генерируется из входного бренд-цвета через blend-алгоритм. Это акцентный цвет бренда; DataLens уже использует именно название `Brand`. Системные цвета (`Blue`, `Red` и т.д.) остаются нетронутыми и про семантику (info, danger), не про акцент.
  - Alpha: `<NewBrand>/<Theme>/Brand/50` .. `<NewBrand>/<Theme>/Brand/500` (10 штук, без суффикса)
  - Solid: `<NewBrand>/<Theme>/Brand/50 Solid` .. `<NewBrand>/<Theme>/Brand/1000 Solid` (20 штук)
- **Системные цвета** (`White`, `Black`, `Blue`, `Green`, `Yellow`, `Red`, `Purple`, `Cool Grey`, `Orange`) — копируются из базового бренда без изменений. Значения захардкожены в плагине из дампа YC Private Colors (стабильная базовая палитра).

Темы кодируются **в именах переменных** (без collection modes), как в существующих файлах: `Light`, `Dark`, `Light-HC`, `Dark-HC`.

Итого: ~272 переменных на тему × 4 темы ≈ **1090 переменных** (аналогично существующим брендам).

После генерации дизайнер публикует файл как библиотеку и подключает к ветке основной либы.

#### Phase 2 — основная либа (ветка)

**В коллекцию Appearance** добавляется новая группа с префиксом `<NewBrand>/`, содержащая ~142 переменных, повторяющих структуру существующих брендов:

- Branding/* (~14 токенов) — алиасятся на новые private brand-примитивы из Phase 1 файла.
- Text/*, Base/*, Base Semantic/*, Base Float/*, Line/*, Misc/*, Effect/*, Navigation/* (~128 токенов) — алиасятся на соответствующие токены **базового бренда** (например, `Yandex Cloud/Text/Primary`).

У каждой переменной — 4 значения по модусам Appearance.

**В коллекцию Brand** добавляется новая колонка-модус с именем бренда. В этом модусе каждая из ~215 переменных Brand-коллекции алиаситься на соответствующий `<NewBrand>/...` из Appearance.

### 4.2. Алгоритм генерации private brand-цветов

Алгоритм — общий с Themer. Параметры различаются по 4 темам.

**Общая логика для каждой темы:**

1. Индекс 550 = базовый бренд-цвет, одинаков во всех 4 темах.
2. Индексы 50–500 (alpha-канал): `rgba(<brand>, opacity)` где opacity = индекс/550. Не зависит от темы.
3. Индексы 50–500 Solid: linear blend бренд-цвета с **primary background** темы (видим бренд через прозрачность поверх фона).
4. Индексы 600–1000 Solid: linear blend бренд-цвета с **contrasting background** темы (затемнение/осветление в сторону противоположного фона).

**Параметры по темам** (берутся из существующего `Yandex Cloud/Branding/Base Background` в либе или из конвенции Gravity):

| Тема       | Primary bg | Contrasting bg |
|------------|------------|----------------|
| Light      | `#FFFFFF`  | `#2D2C33`      |
| Dark       | `#2D2C33`  | `#FFFFFF`      |
| Light HC   | `#FFFFFF`  | `#222326` (темнее, чем у обычной Light) |
| Dark HC    | `#222326`  | `#FFFFFF`      |

Точные значения HC primary/contrasting фонов нужно прочитать из существующих переменных `Yandex Cloud/Branding/Base Background` в либе при инициализации плагина — это источник истины.

**Что из этого даёт публичный API @gravity-ui/uikit-themer:**

Функция `updateBaseColor` принимает `themeVariant: 'light' | 'dark'` — то есть отрабатывает только обычные Light/Dark. HC вариантов в публичном API нет. Для HC надо либо вызвать ту же низкоуровневую blend-функцию с HC-фонами (если она экспортируется или может быть экспортирована через PR в апстрим), либо реализовать blend-функцию самостоятельно — она достаточно простая (линейная интерполяция в sRGB или OKLab).

См. ADR-002 (`docs/decisions/0002-hc-themes-generation.md`).

### 4.3. Архитектура самого плагина

Стандартная для Figma-плагина двухпроцессная схема:

- **Main thread** (внутри Figma): имеет доступ к `figma.variables` API. Читает существующие коллекции, валидирует, записывает новые переменные/модусы/значения, читает фоны из существующих Branding-токенов.
- **UI thread** (HTML iframe): рендерит визард, превью, форму экспорта. Общается с main thread через `postMessage`.

**Поток данных:**

```
[UI: ввод бренд-цвета]
    → postMessage в main
    → main: считывает фоны из либы
    → main: дёргает themer + кастомный HC blend
    → main: возвращает в UI все ~124 значения private brand
    → UI: рендерит превью с этими значениями (как CSS-переменные внутри iframe)
    → [пользователь подтверждает]
    → UI: postMessage в main с "commit"
    → main: пишет в коллекции Private Colors, Appearance, Brand
    → main: postMessage в UI: готово
    → UI: показывает кнопку "Download CSS"
```

### 4.4. CSS экспорт

Формат — тот же, что у Themer'а ([образец в `docs/themer-output-example.css`](docs/themer-output-example.css), приведённый из исходного обсуждения):

- `.g-root` — общие шрифты.
- `.g-root_theme_light`, `.g-root_theme_dark`, `.g-root_theme_light-hc`, `.g-root_theme_dark-hc` — частные переменные `--g-color-private-brand-*` + переопределения Branding-токенов (`--g-color-base-brand`, `--g-color-text-link` и т.д.).

Плагин формирует строку CSS и предлагает скачать как `<brand-name>.theme.css`.

## 5. Пользовательский сценарий (визард)

### 5.1. Базовый режим

1. Дизайнер создаёт ветку центрального файла либы (через Figma UI).
2. В этой ветке открывает плагин Brand Manager.
3. Шаг "Welcome": выбор режима (Basic / Expert). По умолчанию Basic.
4. Шаг "Brand identity": ввод имени бренда. Валидация: уникальность (нет колонки с таким именем в Brand-коллекции), безопасность для использования как префикс (только латиница/цифры/пробел/тире).
5. Шаг "Base brand": выбор базового бренда из списка существующих (YC, YC 2026, Gravity, Yandex Beta, Orbita, DataLens). По умолчанию YC.
6. Шаг "Brand color": ввод бренд-цвета. Поле hex, нативный color picker, и (опционально) поле для отдельных значений Light и Dark — иногда дизайн требует, чтобы в светлой и тёмной темах акцент был немного разный.
7. Шаг "Preview": в окне плагина рендерится демка компонентов (кнопка primary, ссылка обычная и visited, выделение текста, заголовок Heavy-вариант) на фоне каждой из 4 тем. Под демкой — шкала private brand-цветов. Дизайнер может вернуться назад и подкрутить цвет.
8. Шаг "Confirm & commit": плагин показывает summary (какие переменные будут созданы, в какие коллекции). По кнопке "Add brand to library" — запись в файл.
9. Финальный экран: "Done. Submit the branch for review when ready." Кнопка "Download CSS for engineering". Возможность закрыть плагин.

### 5.2. Экспертный режим

Те же шаги, плюс дополнительные:

- На шаге "Base brand" опция "Use custom Private Colors library" — поле для вставки JSON-описания внешней либы примитивов (получаемого через утилиту-Dumper, аналог нынешней). При наличии этого JSON плагин будет привязывать Appearance-токены к внешним переменным вместо общих Private Colors.
- Дополнительные шаги конфигурации в будущих версиях (точечные overrides Text/Base/...) — заглушки для расширения.

## 6. Стек

- **TypeScript** — основной язык.
- **Figma Plugin API** (`@figma/plugin-typings`) — типизация Figma-окружения.
- **`@gravity-ui/uikit-themer`** — generation Light/Dark private colors из бренд-цвета.
- **Bundler**: esbuild (быстро, минимальная конфигурация). Альтернатива — vite + plugin для Figma.
- **UI**: чистый HTML + TypeScript + минимум CSS. Возможно тонкий слой компонентов (Preact/Lit) если будет нужно — но в идеале без фреймворка.

Никаких HTTP-запросов из плагина не делаем (это упрощает и аудит, и manifest). Themer работает локально как npm-пакет.

## 8. Документация и контекст для Claude Code

Claude Code при работе в репозитории автоматически подхватывает `CLAUDE.md`. Помимо него полезно:

- **`CLAUDE.md`** — компактный (≤2 экранов) контекст: что такое проект, ключевые архитектурные решения (без подробностей), конвенции кода, какие файлы читать первым делом, где искать спеки. Обновляется по мере проекта.
- **`SPEC.md`** — точные продуктовые требования (детализация раздела 5 этого плана), включая edge cases, валидации, copy для UI. Это reference-документ для повседневной работы.
- **`docs/architecture.md`** — карта переменных, потоки данных, диаграмма коммуникации main↔UI. Если в будущем кто-то новый придёт смотреть код — это первое, что нужно читать после CLAUDE.md.
- **`docs/decisions/*.md`** — короткие ADR для каждого ключевого решения (~half-page каждая). Зафиксированы здесь, чтобы избежать передумывания. Формат: Контекст → Решение → Последствия.
- **`docs/lib-dumps/*.json`** — дампы переменных из существующей либы (опен-сорс и внутренней), полученные через текущий Dumper-плагин. Будут полезны Claude Code как референс структуры и для тестов.

## 9. Открытые вопросы

Эти решения не блокируют старт работы — можно начать строить и определиться по ходу:

- **Color picker UX**: один цвет на оба темы или два отдельных поля Light/Dark с самого начала? Лёгкий контроль "advanced: different per theme".
- **Preview content**: какие именно компоненты показывать? Минимум: primary button, secondary button, link, link visited, selection (выделенный текст), карточка с заголовком и текстом. Возможно: input, checkbox, toast.
- **Brand naming**: разрешать ли кириллицу в имени бренда? Влияет на ключи Figma-переменных. Безопаснее — только латиница.
- **Конфликты имён**: что показывать дизайнеру, если "Orbita" уже есть? Только ошибка, или предложение "Edit existing" (но в v1 edit вне скоупа — пока только ошибка).
- **Telemetry**: нужны ли метрики использования плагина (количество созданных брендов, частые ошибки)? Если да — куда отправлять. В v1 можно без этого.
- **Локализация UI**: пока однозначно ru. На случай расширения — выделить строки в один файл.
- **Black Rock**: в YC Private Colors есть семейство `Black Rock` — всего 3 переменные (Dark/850, Dark-HC/850, Dark-HC/950), значения в диапазоне тёмных фоновых цветов (~`#2D2B33`). В Appearance и Brand коллекциях ни на что не ссылается. Природа и предназначение неизвестны — возможно ранний артефакт. Пока копируется в новый бренд как есть; выяснить у DS-команды, нужно ли его включать или можно дропнуть.

## 10. Последовательность работ

Разбито на milestone'ы, каждый ~1–2 дня работы Claude Code + ревью.

### Milestone 0 — Bootstrap репозитория

- Создать репо, инициализировать `package.json`, `tsconfig.json`, `.gitignore`.
- Накатить `manifest.json` для плагина с минимальной конфигурацией (доступ к Variables, UI размер).
- Базовая структура `src/` (см. раздел 7).
- esbuild-конфиг, dev/build скрипты.
- Hello-world плагин: открывается окно, показывает "Hello", main thread пишет в консоль и закрывается.
- README, CLAUDE.md, SPEC.md, PLAN.md (этот документ), 1–2 первых ADR.
- Залить в локальный git, проверить пока без GitHub.

### Milestone 1 — Чтение либы и валидация

- В main thread: функции читать существующие коллекции (`figma.variables.getLocalVariableCollections()`), достать список брендов из коллекции Brand, достать фоны из `*/Branding/Base Background` каждой темы.
- Валидатор: проверка уникальности имени бренда, проверка наличия базового бренда, ругательство при отсутствии нужных коллекций.
- В UI: пока заглушка — кнопка "Show me what's in the lib", показывает в окне плагина результат inspect.

### Milestone 2 — Themer integration + HC blend

## 11. Зависимости и риски

**Технические риски:**

- `@gravity-ui/uikit-themer` не экспортирует низкоуровневую blend-функцию → придётся реализовывать самим. Митигация: написать собственную функцию, сверить с эталонным выводом Themer'а через unit-тесты.
- Figma Variables API ограничен по числу алиасов в транзакции / производительности при массовой записи → митигация: батчинг, прогресс-индикатор в UI.
- Figma может изменить лимиты модусов обратно → митигация: не закладываемся жёстко на "много модусов", архитектура работает и при 10.

**Продуктовые риски:**

- Дизайнеры могут начать массово создавать "одноразовые" бренды → митигация: ревью на уровне веток, наличие "Delete" в v2.
- Naming-конвенции разойдутся (один пишет "DataLens", другой "datalens") → митигация: валидатор имён, может быть автоформат "Title Case".
